# Human Gates：什么时候找人、怎么找人

目标：人只做机器做不好的判断，而且每次判断都**快**（≤ 5 分钟）、**准**（选择题 + 推荐）、**不打断**（批量、非阻塞）。

## 1. 必须开人工门的情况

| 类别 `kind` | 触发条件 | 机器必须先做完的预检 |
|---|---|---|
| `design` 设计决策 | 架构取舍、数据模型、对外 API 形状、引入新服务/新依赖类别 | 2–3 个方案，每个列：改动量、风险、可逆性、长期成本；给推荐 |
| `ui` UI/UX | 新增/改版页面、交互流程、视觉样式、文案 | 启动本地服务；Playwright 截图 375/768/1440 三种宽度（亮/暗色如适用）；关键流程录屏或步骤截图；a11y 扫描结果；与改动前截图并排 |
| `sensory` 感官 | 音频/语音生成、音乐、视频编码/推流、动画手感、触感 | 可量化指标先过：音频（时长、采样率、响度 LUFS、峰值/削波、静音段）；视频/推流（分辨率、帧率、码率、关键帧间隔、丢帧率、端到端延迟、音画同步偏差）；输出样本文件和 A/B 对照 |
| `irreversible` 不可逆 | 合并到 main、部署任何非本地环境、数据迁移、删除数据/文件/分支、发版打 tag | diff 摘要、测试结果、dry-run 输出、回滚方案 |
| `external` 外部影响 | 发消息/邮件/评论、花钱、改权限/密钥/DNS、调用生产 API | 草稿全文、影响对象、可否撤回 |
| `ambiguity` 需求歧义 | 任务卡存在两种合理理解且结果差异大；范围需要扩大 | 列出各理解及后果；推荐一种 |
| `unlock` 解锁 | 需要修改 locks 中的路径 | 为什么必须改、影响哪些下游任务、替代方案 |

**不要**为以下事情开人工门（自己决定并在任务卡记录理由）：命名、内部实现细节、测试写法、可轻易回滚的小选择、有明确项目约定可循的事情。

## 2. 怎么开：`/harness:human-gate`

用 `/harness:human-gate <kind> <一句话问题>` 生成 `.harness/gates/G-Txxx-n.md`（模板见 `.harness/gates/_TEMPLATE.md`）。每张卡必须包含：
1. **一句话问题**（选择题优先，例如「播放器倍速选择器用 A 下拉 / B 分段按钮？」）。
2. **为什么机器决定不了**（一句）。
3. **怎么检查**：可直接复制的命令、URL、文件路径，以及按顺序的检查步骤；预计耗时。
4. **机器已预检**：指标表 + 通过/不通过。
5. **选项**：A/B/C，每个一句话后果；标出推荐及理由。
6. **默认行为**：如果 24h 无答复/无人值守时，会怎么做（通常：继续推荐方案但不合并，或保持 blocked）。
7. **阻塞范围**：哪些任务/步骤被它阻塞，哪些不受影响。
8. **紧急度** `urgency`：`high` = 阻塞多个任务或有时效（会标 🔴 并加 `urgency:high` 标签）；`low` = 不急、可攒着批；其余 `normal`。不要什么都标 high。

## 3. 怎么沟通
- **批量**：同一轮发现的多个问题合并成一次通知；能放在任务收尾时一起问的不在中途问。
- **非阻塞**：开门后把任务卡标为 `waiting_human`（仅当后续步骤全都依赖答复），否则继续做不依赖答复的部分。无人值守时转去做其他 `ready` 任务。
- **选择题**：门卡写成选择题（2–4 个选项，推荐项放第一个并标注「推荐」）；批准项固定是 A。
- **答复处理**：答复只由用户给，由控制面写进仓库外的答案库，同一张门卡只认第一次。五个通道写同一个库：
  - 终端：用户自己跑 `harness_lib.py answer G-Txxx-n <选项> [备注]`（先 `show G-Txxx-n` 看含义）；
  - 看板：`harness serve` 打印的带令牌地址；
  - GitHub：在门卡 Issue 勾选或回复通知邮件；合并类门卡 = PR 合并 / 关闭；
  - 对话：交互会话里点 AskUserQuestion 选项卡，或整条消息恰好是 `G-Txxx-n: <选项> [备注]`（有后续效果的批准不从对话记录）；
  - Telegram：`harness inbox setup` 配对后点手机上的按钮，批准要二次确认。
  门卡上的 `status` / `answer` / `decided_by` 和 decisions.md 是控制面写的镜像：Claude 只开卡，从不写、不改 `answer` 等字段，改了也不生效（看板标「答案不一致」）。
  解除阻塞、`then: ready`、接续都由控制面按答案库处理；对话里通道没记录时，请用户用其他任一通道答复。
- **不重复问**：先查 `.harness/decisions.md`，已有决定的同类问题直接沿用并引用决策编号。
- **会弹确认的操作放最后一起跑**：即使某个不可逆操作已获批准，也先做完其他所有步骤（写文件、提交、更新任务卡），最后把所有会弹确认的命令连续执行，让人只被打断一次。无人值守时 hook 会拒绝这类命令：把命令原样记进任务卡「7. 当前进展 → 待人执行」，继续其他工作。
- **只报增量**：回复里的待决区块只列新增或状态有变化的项目，结尾一行写「还有 N 项未决」；完整清单只在被问到或最终汇报时列出。

## 4. 回复里的「待你决定」区块（`decision_guard.py` 会检查）
回复末尾如有需要人决定的事，放在标题为「待你决定」（或 `Decisions Needed`）的区块里，每一项必须：
- 引用门卡编号（`G-T013-2`，推荐——门卡持久化，信息都在卡里），**或者**
- 以类别标签开头：`[design]` `[ui]` `[sensory]` `[irreversible]` `[external]` `[ambiguity]` `[unlock]`（或中文 `[设计]` `[界面]` `[感官]` `[不可逆]` `[对外]` `[歧义]` `[解锁]`）；
  - `[ui]` / `[sensory]` 必须写怎么检查（反引号命令、URL 或文件路径）；
  - `[design]` / `[ambiguity]` 必须写两边各自的得失。

套不进任何类别的事，是你自己该做的：直接做掉，列为已完成，不要问。

## 5. 合并（irreversible 的最常见情形）
任务 `review` 状态后：
1. 推送任务分支，开 PR（`gh pr create`，正文用交接包内容），**不合并**。
2. 门卡附：PR 链接、`git diff --stat`、验证命令结果、verifier 结论、回滚方式（`git revert <merge-commit>`）。
3. 人批准后由人点击合并，或人明确回复「G-Txxx-n: 合并」后 Claude 才可执行合并命令（此时需人在交互式会话中确认 hook 的提示）。
