为下一轮迭代挑任务。只读，不修改文件。

开始前，先列出有经验的技术负责人做这件事时实际用的方法和工具（例如：读最近的错误日志找高频崩溃、按调用次数看热点、跑依赖审计、看 TODO/FIXME 的分布、对照 spec 找未覆盖的验收），然后逐项执行。不要靠身份设定，靠方法。

## 维度与典型信号
| 维度 | 去哪里找 |
|---|---|
| 功能完整性 | TODO/FIXME、空 catch、未处理的错误状态/空状态/加载状态、交接包遗留问题、只实现了 happy path 的流程 |
| 测试 | 无测试的模块（对比 src 与 tests 目录）、只有快照没有行为断言、关键路径无 E2E |
| 部署与 CI | 有没有 CI；是否跑测试/lint/构建；是否有预发环境；回滚方式；环境变量文档；Dockerfile 是否多阶段、非 root |
| 性能 | N+1 查询、未分页的列表接口、大 bundle、未压缩图片、同步阻塞 IO |
| 可观测性 | 结构化日志、错误上报、关键业务指标、健康检查接口 |
| UX 与无障碍 | 表单校验反馈、键盘可达、对比度、移动端适配、i18n 硬编码字符串 |
| 文档 | README 能否让新人 15 分钟跑起来、API 文档、架构决策记录 |

## 规则
- 每条提议必须给出**证据位置**（文件:行 或 命令输出），没有证据不提。
- 优先「做完能明显降低风险或解锁后续工作」的；不要提纯风格偏好的重构。
- 一条提议控制在 S/M 规模；L 规模给出拆分建议。
- 最多 12 条。

## 输出
```
PROPOSALS:
- title: <动词开头的一句话>
  dimension: <维度>
  evidence: <文件:行 / 命令输出>
  why: <一句话价值>
  acceptance: <1–2 条可验证的验收标准>
  allowed_paths: [<glob>]
  priority: P0|P1|P2|P3
  risk: low|medium|high
  size: S|M
  auto_ok: yes|no   # 仅补测试/文档/lint/patch 级依赖升级/只加日志指标可为 yes
```
